# ADR-002: Запуск кода студентов

## Status

Proposed

## Context

В рамках сервиса проверки необходимо запускать код студентов для проверки работоспособности, соответствия критериям и дальнейшему выставлению оценки. Необходимо определить механизм для запуска кода с соблюдением требований безопасности:

- Запускаемый код не должен иметь доступ к LMS и данных хранящихся в ней.
- Запускаемый код не должен иметь доступ к данным других студентов выполняющих задания в Сервисе проверки.
- Ресурсы потребляемые при запуске кода должны регулироваться для определения лимитов.
- Ошибки при исполнении кода не должны влиять на доступность Сервиса проверки для других пользователей.

## Decision

Для безопасности код студентов исполняется в изолированном Docker-контейнере, запускаемом по требованию, на отдельном узле (runner-ноде), изолированном от узлов с бизнес-логикой Сервиса проверки. Контейнер создается во время одной проверки с настроенными политиками безопасности:

- Сеть полностью отключена (network mode: none). Код студента не имеет доступа ни к внутренним, ни к внешним ресурсам.
- Ограничение ресурсов (CPU, память, время выполнения).
- Запуск от пользователя с ограниченными правами.
- Доступ только к выбранной части файловой системы.

## Consequences

Положительные:

- Гибкость настройки изоляции контейнера: CPU, память, доступ к сети, read-only для файловой системы и тп.
- Поддержка комьюнити, богатая документация, готовые решения и конфигурации.
- Умеренные временные затраты на разработку.
- Высокая скорость запуска контейнера. Секунды или доли секунды.
- Низкий порог входа для команды, уже знакомой с Docker.
- Быстрое добавление новой функциональности и итерация: изменения в политике изоляции и лимитах вносятся силами команды, без внешних вендоров и согласований.

Отрицательные:

- Хоть и ограниченный, но доступ к ядру ОС создаёт теоретический риск эксплойта — в отличие от микро-VM с собственным ядром
- Требует подробного изучения документации и ручной поддержки.
- Большое число параметров конфигурации создаёт риск ошибок, требуется высокая экспертиза команды разработки и ревью конфигурации
- Отсутствие внешней поддержки: все инциденты и обновления — зона ответственности команды
