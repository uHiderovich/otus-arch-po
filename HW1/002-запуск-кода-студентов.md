# ADR-002: Запуск кода студентов

## Status

Proposed

## Context

В рамках системы автоматической проверки необходимо запускать код студентов для проверки работоспособности, соответствия критериям и дальнейшему выставлению оценки. Необходимо определить механизм для запуска кода с соблюдением требований безопасности:

- Запускаемый код не должен иметь доступ к LMS и данных хранящихся в ней.
- Запускаемый код не должен иметь доступ к данным других студентов выполняющих задания в системе автоматической проверки.
- Ресурсы потребляемые при запуске кода должны регулироваться для определения лимитов.
- Ошибки при исполнении кода не должны влиять на доступность системы автоматической проверки для других пользователей.

## Decision

Код студентов исполняется во временных Docker-контейнерах на отдельном сервере проверок, отдельно от Backend API и хранилищ. Контейнер создаётся для одной проверки с настроенными политиками безопасности:

- Сеть полностью отключена (network mode: none). Код студента не имеет доступа ни к внутренним, ни к внешним ресурсам.
- Ограничение ресурсов (CPU, память, время выполнения).
- Запуск от пользователя с ограниченными правами.
- Доступ только к выбранной части файловой системы.

Выбор Docker-контейнеров предварительный, с учётом ограниченного бюджета и сложности сопровождения. Перед эксплуатацией нужно оценить, достаточно ли такой изоляции для запуска недоверенного кода.

## Alternatives

- **Docker-контейнеры на отдельном сервере проверок.** Выбранный вариант: знакомые инструменты и сравнительно простой запуск проверок. При этом остаётся риск общего ядра с хостом.
- **gVisor.** Добавляет слой изоляции между программой и ОС хоста. Пока не выбран: нужно проверить совместимость с используемыми языками и влияние на время проверки.
- **Kata Containers.** Запускает контейнеры в лёгких виртуальных машинах с отдельным ядром. Пока не выбран: потребуется настроить и сопровождать среду виртуализации.
- **microVM, например Firecracker.** Позволяет выполнять работы в отдельных лёгких виртуальных машинах. Пока не выбран: потребуется организовать создание образов, запуск и управление этими машинами.

Причины выбора предварительные: совместимость, затраты и сложность сопровождения альтернатив ещё не проверялись на практике. Решение может быть пересмотрено по результатам оценки безопасности.

Описание вариантов: [gVisor](https://gvisor.dev/docs/), [Kata Containers](https://katacontainers.io/), [Firecracker](https://firecracker-microvm.github.io/).

## Consequences

Положительные:

- Гибкость настройки изоляции контейнера: CPU, память, доступ к сети, read-only для файловой системы и тп.
- Поддержка комьюнити, богатая документация, готовые решения и конфигурации.
- Умеренные временные затраты на разработку.
- Высокая скорость запуска контейнера. Секунды или доли секунды.
- Низкий порог входа для команды, уже знакомой с Docker.
- Быстрое добавление новой функциональности и итерация: изменения в политике изоляции и лимитах вносятся силами команды, без внешних вендоров и согласований.

Отрицательные:

- Docker-контейнеры используют общее ядро с хостом. Ограничения доступа и ресурсов снижают риск, но не обеспечивают абсолютную изоляцию недоверенного кода. Уязвимость ядра или среды выполнения может привести к выходу за пределы контейнера.
- Требует подробного изучения документации и ручной поддержки.
- Большое число параметров конфигурации создаёт риск ошибок, требуется высокая экспертиза команды разработки и ревью конфигурации
- Отсутствие внешней поддержки: все инциденты и обновления — зона ответственности команды
