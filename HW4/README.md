## Структура системы

За основу решения взят вариант 2 функциональной декомпозиции из ДЗ 2 и сценарий из ДЗ 3.

### Приложения и сервисы

- **Web-приложение**. Пользовательский интерфейс для входа в систему, загрузки работ, создания и изменения заданий для студентов: дедлайна и критериев проверки. Позволяет просматривать статус и результаты проверки. Подробнее: [аутентификация и авторизация](#аутентификация-и-авторизация).

- **Backend API**. Проверяет права пользователя на действия в системе, управляет заданиями и критериями. Сохраняет попытку в истории, ставит работу в очередь на проверку и отслеживает её статус в PostgreSQL. Отправляет работу на проверку в сторонние сервисы и сохраняет их результаты в PostgreSQL. Когда все обязательные проверки завершены, объединяет их результаты, формирует итоговую оценку и сохраняет её в базу. Инициирует передачу оценки в LMS и отправляет событие в очередь уведомлений. Подробнее: [аутентификация и авторизация](#аутентификация-и-авторизация), [формирование итоговой оценки](#формирование-итоговой-оценки).

- **Сервис проверки работ**. Получает задание из очереди в PostgreSQL. Читает из S3 файлы работы и критериев, а из PostgreSQL — метаданные с параметрами запуска. По этим параметрам запускает работу и проверки в отдельном Docker-контейнере. Сохраняет результаты выполнения и обновляет статус задания в PostgreSQL. Ограничивает число одновременно запущенных контейнеров и останавливает их при превышении времени выполнения. Подробнее: [обработка задания на проверку](#обработка-задания-на-проверку).

- **Сервис уведомлений**. Получает сообщения из очереди уведомлений и отправляет уведомления пользователям через сервис отправки Email.

### Хранение данных

- **Основная база системы**. Используется PostgreSQL. Хранит задания, дедлайны, версии критериев, историю попыток, результаты выполнения тестов и проверки на плагиат, итоговые оценки и очередь работ на проверку. Хранит статусы отдельных проверок и события, ожидающие отправки в RabbitMQ и LMS. Также хранит ссылки на файлы в S3 и метаданные с параметрами запуска работ и проверок. Каждая попытка связана с версией критериев, по которой выполнялась проверка.

- **S3-хранилище**. Хранит файлы работ студентов, файлы критериев проверки, отчёты и логи запусков. В PostgreSQL сохраняются ссылки на эти файлы и сведения о соответствующей попытке и запуске.

### Очередь уведомлений

- **RabbitMQ**. Хранит сообщения для отправки уведомлений. Backend API добавляет сообщения в очередь, а сервис уведомлений получает и обрабатывает их.


## Развёртывание

Предварительно предполагается размещение на Linux-серверах:

- **Сервер приложений**. Веб-сервер и обратный прокси, Backend API и сервис уведомлений запускаются в отдельных Docker-контейнерах. Для начального варианта предусмотрен один экземпляр каждого приложения.
- **Сервер данных**. PostgreSQL, RabbitMQ и S3-совместимое файловое хранилище запускаются в отдельных Docker-контейнерах. Данные сохраняются отдельно от контейнеров и остаются доступными после их пересоздания.
- **Сервер проверок**. Диспетчер проверок работает как Java-процесс под управлением systemd. Через Docker Engine он запускает до пяти временных контейнеров одновременно. Каждый контейнер проверяет одну работу.

Это предварительный вариант размещения. Количество серверов, их ресурсы и распределение приложений требуют обсуждения с учётом бюджета и ожидаемой нагрузки. Linux-серверы могут быть физическими машинами или виртуальными машинами.

На диаграмме контейнеров сервис проверки работ показан укрупнённо. На диаграмме развёртывания раскрыты его состав и размещение: постоянно работающий диспетчер и временные исполнители отдельных работ.

При недоступности сервера данных получение заданий и сохранение результатов приостанавливаются до восстановления доступа. Размещение и порядок создания резервных копий остаются открытыми вопросами.


## Аутентификация и авторизация

- **Аутентификация** студентов и преподавателей выполняется средствами LMS. Предполагается, что LMS предоставляет API для аутентификации и получения сведений о пользователе, включая его уникальный идентификатор и роли.

- Система автоматической проверки не хранит пароли пользователей.

- Проверка прав доступа к заданиям, попыткам и результатам выполняется в Backend API на основании роли пользователя и его полномочий.

- Конкретный протокол интеграции с LMS требует уточнения. Предпочтительно использование стандартного механизма единого входа.


## Обработка задания на проверку

### Когда работа считается принятой

Работа считается принятой по результатам проверки, когда она удовлетворяет всем основным критериям задания. Дополнительные критерии могут влиять на оценку. Состав критериев и их влияние на оценку определяются при создании задания.

Отдельно фиксируется приём работы на проверку. После загрузки файлов Backend API одной транзакцией сохраняет попытку и задание в очереди PostgreSQL. После этого студент получает подтверждение, что работа поставлена на проверку. Каждая новая отправка студента создаёт отдельную попытку. Повтор после технического сбоя относится к той же попытке.

### Получение задания

Сервис проверки работ в фоне периодически запрашивает задания со статусом «Ожидает проверки». Интервал опроса задаётся в конфигурации. Сервис берёт задание, когда у него есть свободное место для запуска контейнера.

Диспетчер выбирает задание и меняет его статус на «Выполняется» одной короткой транзакцией. Это защищает задание от одновременного получения другим диспетчером. После получения задания транзакция завершается, а проверка выполняется отдельно. Для выбора задания используется блокировка строки через `FOR UPDATE SKIP LOCKED`.

В базе сохраняются идентификатор исполнителя, уникальный идентификатор запуска, время начала, срок владения заданием и число технических повторов. При каждом повторе создаётся новый идентификатор запуска.

### Ограничение ресурсов

На сервере проверок работает один диспетчер. В его конфигурации задаётся лимит в пять одновременно запущенных контейнеров. Ограничения CPU и памяти для каждого контейнера и максимальное время выполнения работы подбираются с учётом ресурсов сервера и требований задания.

Если свободных мест нет, задания остаются в очереди.

### Доступ студенческого кода

Для каждой работы создаётся отдельный временный контейнер. Диспетчер передаёт в него код студента, файлы тестов и конфигурацию проверки. Образ со средой выполнения выбирается по настройкам задания.

Контейнеру доступны только файлы текущей проверки и отдельный каталог для результатов. Файлы других работ, пароли подключения к хранилищам и Docker API ему недоступны. Контейнер запускается без привилегированного режима, с ограниченными правами и отключённой сетью. Все необходимые зависимости заранее включаются в образ.

Диспетчер загружает файлы из S3 и сохраняет полученные отчёты и логи в S3. Статусы, результаты проверок и ссылки на файлы записываются в PostgreSQL. После сохранения результатов временный контейнер и его рабочие файлы удаляются.

### Зависания и технические сбои

Сервис проверки следит за временем выполнения каждого контейнера. Если студенческая программа превысила допустимое время, сервис останавливает контейнер, сохраняет результат «Превышено время выполнения» и лог запуска. Студент получает уведомление о превышении времени выполнения, чтобы проверить свой код, например на бесконечный цикл. Backend API создаёт событие для сервиса уведомлений после сохранения результата. Влияние этого результата на оценку определяется критериями задания.

Пока диспетчер обрабатывает задание, он периодически продлевает срок владения в PostgreSQL. Интервал продления и срок владения задаются в конфигурации отдельно от максимального времени выполнения программы.

Фоновый обработчик сервиса проверки ищет задания с истёкшим сроком владения. Он переводит их в очередь для повторной проверки, если число технических повторов ещё не исчерпано. Проверка срока и изменение статуса выполняются атомарно. После исчерпания повторов обязательно сохраняются техническая ошибка и лог с доступными сведениями о запусках и причинах сбоев. Студент получает уведомление, что проверку не удалось завершить из-за технической ошибки. Сообщение о превышении времени выполнения отправляется, если зафиксировано именно превышение лимита программы.

Единичный сбой фиксируется в истории и логах. При массовых технических сбоях уведомляются разработчики. Порог числа ошибок и интервал наблюдения задаются в конфигурации системы.

На каждом хосте сервис проверки также сверяет запущенные Docker-контейнеры с заданиями в базе. Для этого контейнеры помечаются идентификаторами заданий и запусков. Контейнеры, превысившие время выполнения или потерявшие право на обработку задания, останавливаются и удаляются. После перезапуска сервис выполняет такую же сверку перед получением новых заданий. Пока хост недоступен, его контейнеры могут оставаться запущенными, но их устаревшие результаты отклоняются.

Диспетчер проверок запускается на Linux-сервере под управлением systemd. Если процесс завершается с ошибкой, systemd перезапускает его.

Для обнаружения зависаний используется watchdog. Диспетчер периодически отправляет systemd сигнал о своей работоспособности. Если сигнал не поступает в течение заданного времени, systemd останавливает диспетчер и запускает его заново. Интервал отправки сигналов и допустимое время ожидания задаются в конфигурации.

После перезапуска диспетчер сверяет запущенные контейнеры с заданиями в PostgreSQL и восстанавливает обработку. Время выполнения студенческой программы контролируется отдельно диспетчером.

### Сохранение результата и защита от повторов

Диспетчер получает результат от исполнителя одной работы, сохраняет его и переводит задание в статус «Завершено» одной транзакцией. Запись разрешается только для текущего идентификатора запуска с действующим сроком владения. Проверка этого условия и сохранение выполняются атомарно.

Если задание уже передано другому исполнителю, результат старого запуска отклоняется. Завершённое задание повторно из очереди не выдаётся. При сбое до сохранения результата выполнение может повториться, но в базе фиксируется результат только действующего запуска.

Данные, уже сохранённые в PostgreSQL и S3, используются при повторной проверке. Промежуточные результаты из памяти или временных файлов остановленного контейнера могут быть потеряны.

## Формирование итоговой оценки

1. Диспетчер проверок сохраняет в PostgreSQL результаты выполнения тестов для конкретной попытки.
2. Backend API сохраняет в PostgreSQL идентификатор запроса во внешний сервис, статус проверки на плагиат и полученный результат. Эти данные связаны с той же попыткой. Большой отчёт при необходимости сохраняется в S3, а ссылка на него — в PostgreSQL. Способ получения ответа зависит от API внешнего сервиса.
3. Фоновый обработчик Backend API периодически ищет попытки, для которых завершены все обязательные проверки, но итоговая оценка ещё не сформирована. Отдельные статусы позволяют учитывать любой порядок завершения тестов и проверки на плагиат.
4. Backend API объединяет результаты и рассчитывает оценку по версии критериев, связанной с попыткой. Выполненная проверка может выявить ошибки в работе студента. Техническая ошибка проверки сохраняется отдельно и требует повтора или разбора, прежде чем формировать итоговую оценку.
5. Backend API одной транзакцией сохраняет итоговую оценку и записи о необходимости уведомить студента и передать оценку в LMS. Блокировка строки попытки и уникальность итогового результата защищают от одновременной обработки несколькими экземплярами Backend API.
6. Фоновый обработчик отправляет сохранённое событие в RabbitMQ и отмечает отправку после подтверждения брокера. Сервис уведомлений получает событие и отправляет студенту результат. Передача оценки в LMS также выполняется с учётом сохранённого статуса и повторяется при временной ошибке.

Сохранение события вместе с оценкой называется transactional outbox. Если приложение завершится после записи оценки, событие останется в базе и будет отправлено позже. При сбое после публикации, но до отметки об отправке, событие может попасть в RabbitMQ повторно. Сервис уведомлений учитывает идентификатор события и обрабатывает повторы. Защита от повторной отправки самого письма также зависит от возможностей почтового сервиса.

Для отслеживания заданий и результатов используется периодический опрос PostgreSQL. После перезапуска обработчики проверяют сохранённые статусы и продолжают незавершённую обработку.

## Уведомления студенту

Для одной попытки предусмотрены два отдельных типа уведомлений:

- **Результат проверки работы**. Отправляется один раз после формирования итоговой оценки и содержит результаты проверки.
- **Превышено время выполнения программы**. Отправляется после фиксации тайм-аута, чтобы студент мог проверить свой код. Это отдельное уведомление, которое может прийти раньше итогового результата.

Если для попытки зафиксирован тайм-аут, студент может получить оба уведомления. Повторная обработка одного события не должна создавать новое уведомление того же типа для той же попытки. При окончательной технической ошибке студенту сообщается, что проверку не удалось завершить, как описано в разделе «Зависания и технические сбои».

## Допущения и открытые вопросы

- Размещение на Linux-серверах предварительное. Количество машин, их ресурсы и распределение приложений требуют обсуждения.
- Требуется определить, где хранятся резервные копии, как часто они создаются и как выполняется восстановление. Пересоздание контейнера сохраняет данные на диске, но при потере самого диска потребуется резервная копия.
- Требуется уточнить допустимое время простоя и потери данных при сбое, чтобы выбрать подходящий способ восстановления.
- Предполагается, что LMS предоставляет API для входа и получения данных пользователя. Конкретный протокол интеграции требует уточнения.
