## Структура системы

За основу взят вариант 2 декомпозиции из ДЗ 2 и сценарии из ДЗ 3.

- **Web-приложение на Vue** — загрузка работ, настройка заданий, критериев и дедлайнов, просмотр результатов.
- **Веб-сервер на Node.js** — выдаёт файлы приложения и передаёт API-запросы в Backend API.
- **Backend API на Java** — управляет заданиями и попытками, проверяет права, организует внешние проверки и рассчитывает оценку.
- **Диспетчер проверок на Java** — получает задания из очереди, запускает исполнителей и сохраняет результаты.
- **Исполнитель одной работы** — временный Docker-контейнер, в котором выполняются код студента и тесты.
- **Сервис уведомлений на Java** — получает сообщения из RabbitMQ и отправляет письма через внешний почтовый сервис.

## Хранение данных

| Хранилище | Данные |
| --- | --- |
| PostgreSQL | Задания, дедлайны, версии критериев, попытки, статусы, результаты и оценки. Также очередь проверок, параметры запусков и записи для отправки уведомлений и оценок в LMS. |
| S3 | Код студентов, файлы критериев и тестов, отчёты и логи. Ссылки на файлы хранятся в PostgreSQL. |
| RabbitMQ | Сообщения для сервиса уведомлений. |

Каждая попытка связана с конкретной версией критериев. Результаты тестов и внешних проверок относятся к этой же попытке.

## Развёртывание

Предварительно используются три Linux-сервера:

- **Сервер приложений:** веб-сервер, Backend API, сервис уведомлений и RabbitMQ в отдельных Docker-контейнерах.
- **Сервер данных:** PostgreSQL и S3-хранилище. Данные сохраняются отдельно от контейнеров.
- **Сервер проверок:** один диспетчер под управлением systemd и до пяти временных контейнеров с работами студентов.

Количество серверов и их ресурсы нужно уточнить с учётом бюджета и нагрузки.

## Вход и права доступа

Предполагается вход через LMS с получением идентификатора и роли пользователя. Конкретный способ интеграции пока не определён.

Пароли пользователей система не хранит. Права на задания, попытки и результаты проверяет Backend API.

## Как проходит проверка

1. Backend API проверяет права и дедлайн, сохраняет файлы работы в S3.
2. Попытка и задание в очереди PostgreSQL сохраняются одной транзакцией. После этого студент получает подтверждение приёма.
3. При наличии свободного места диспетчер забирает задание, подготавливает файлы и запускает контейнер с нужной средой выполнения.
4. Исполнитель выполняет код и тесты. Диспетчер сохраняет отчёты и логи в S3, результаты и статус — в PostgreSQL.
5. Backend API организует внешние проверки и сохраняет их результаты.
6. Когда все обязательные проверки завершены, Backend API рассчитывает оценку и организует её передачу в LMS и уведомление студента.

Приём на проверку ещё не означает успешную сдачу: работа должна выполнить все основные критерии задания.

## Запуск и изоляция

Диспетчер выбирает задание короткой транзакцией с `FOR UPDATE SKIP LOCKED`. Для каждого запуска сохраняются его идентификатор и срок владения заданием. Во время обработки диспетчер продлевает этот срок. Сохранить результат может только текущий запуск с действующим сроком владения.

Контейнер получает только файлы своей проверки. Сеть отключена, доступ к другим работам, паролям хранилищ и Docker API отсутствует. Контейнер запускается без привилегированного режима. Зависимости заранее включаются в образ.

CPU, память и время выполнения ограничены. Если все пять мест заняты, работы остаются в очереди. После сохранения результата контейнер и временные файлы удаляются.

## Зависания и технические сбои

Если программа студента превысила время выполнения, диспетчер останавливает контейнер и сохраняет результат тайм-аута с логом. Это результат проверки программы, а не технический сбой. Его влияние на оценку задаётся критериями.

При технической ошибке система автоматически повторяет незавершённые проверки. Число повторов задаётся в конфигурации. Используются сохранённые результаты той же попытки; завершённые проверки повторять не нужно.

Если повторы исчерпаны, ошибка сохраняется, студент получает уведомление. До дедлайна он может вручную возобновить проверку той же попытки. Новая попытка создаётся только при обычной отправке нового решения.

Автоматическая обработка принятой работы может продолжаться после дедлайна. Ручной запуск после дедлайна запрещён; такие случаи разбираются отдельно в рамках учебного процесса.

systemd перезапускает диспетчер при падении или зависании. После перезапуска диспетчер сверяет контейнеры с заданиями в базе и останавливает устаревшие запуски. Их результаты не могут заменить актуальные, хотя само выполнение при сбое может повториться.

При недоступности сервера данных получение заданий и сохранение результатов приостанавливаются. Единичные ошибки остаются в истории и логах, при массовых сбоях уведомляются разработчики.

## Оценка и передача результатов

Backend API периодически ищет попытки с завершёнными обязательными проверками и рассчитывает оценку по сохранённой версии критериев. Пока обязательная проверка не завершена из-за технической ошибки, итоговая оценка не формируется.

Оценка и записи о необходимости уведомить студента и передать результат в LMS сохраняются одной транзакцией — это transactional outbox. Затем фоновые обработчики выполняют отправку и повторяют её при временных ошибках.

Событие может быть доставлено повторно, поэтому сервис уведомлений учитывает его идентификатор. Защита от повторного письма также зависит от возможностей почтового сервиса.

## Уведомления

Студент получает итоговый результат проверки. Отдельно отправляется сообщение о превышении времени выполнения программы — поэтому для одной попытки могут прийти оба уведомления.

После исчерпания технических повторов приходит сообщение о невозможности завершить проверку. Повторная обработка события не должна создавать новое уведомление того же типа для той же попытки.

## Открытые вопросы

- Ресурсы серверов и ожидаемая нагрузка.
- Способ входа через LMS.
- Конкретное хранилище резервных копий, периодичность копирования и порядок восстановления. Копии хранятся отдельно от основных серверов.
- Допустимые простой и потеря данных при сбое.
